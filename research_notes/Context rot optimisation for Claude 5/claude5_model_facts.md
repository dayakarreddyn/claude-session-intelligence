# Claude 5 family context-window facts: Claude Fable 5.1 and Claude Opus 5.5 (as of 2026-10-19)

Scope: Fable 5.1 (`claude-fable-5-1`, same model as Mythos 5.1) and Opus 5.5 (`claude-opus-5-5`). All numbers below are from Anthropic's own docs (platform.claude.com, code.claude.com), announcement posts, or system cards, fetched 2026-10-19. Note that `docs.claude.com` / `docs.anthropic.com` URLs now 302-redirect to `platform.claude.com`. Third-party aggregators were checked only for corroboration and are not used as the source of any number. Anything dated before mid-2026 is flagged `[STALE-RISK]`.

Release dates: Fable 5.1 / Mythos 5.1 released September 1, 2026; Opus 5.5 released September 22, 2026 — [Fable 5.1 overview](https://platform.claude.com/docs/en/models/fable-5-1/overview); [Opus 5.5 overview](https://platform.claude.com/docs/en/models/opus-5-5/overview).

## KQ1. Context window size, max output, and whether a long-context pricing tier exists

### Takeaway
Both models have a 1M-token context window that is the default and maximum (no beta header), 128K max output on the synchronous Messages API, and standard per-token pricing across the whole window — there is no >200K premium tier on either model (the only model with a length-based tier is Haiku 5.5, above 100K prompt tokens).

### Cited Findings
- Models comparison table: Fable 5.1 and Opus 5.5 both list "Context window: 1M tokens", "Max output: 128K tokens", "Reliable knowledge cutoff: Jun 2026", "Training data cutoff: Jun 2026"; retirement "Not sooner than September 1, 2027" (Fable 5.1) and "Not sooner than September 22, 2027" (Opus 5.5) — [Models overview](https://platform.claude.com/docs/en/models/overview)
- "For every model with a 1M-token context window, 1M is the default: you don't need a beta header, and long-context requests are billed at standard pricing, except on Claude Haiku 5.5, where prompts over 100,000 tokens cost more." Models listed with 1M: Fable 5.1, Mythos 5.1, Fable 5, Mythos 5, Opus 5.5, Opus 5, Opus 4.8, 4.7, 4.6, Sonnet 5.5, Sonnet 5, Sonnet 4.6, Haiku 5.5, Mythos Preview. "A single request to any of them can generate up to 128k output tokens (`max_tokens`)." — [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)
- Long context pricing: "Claude 4.6 and later models (except Claude Haiku 5.5) and Claude Mythos Preview include the full 1M token context window at standard pricing. (A 900k-token request is billed at the same per-token rate as a 9k-token request.) Prompt caching and batch processing discounts apply at standard rates across the full context window." — [Pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Fable 5.1/Mythos 5.1 spec: "a 1M token context window (default and maximum) at standard per-token pricing across the whole window, and 128k max output tokens." — [What's new in Fable 5.1](https://platform.claude.com/docs/en/models/fable-5-1/whats-new-fable-5-1)
- Extended output on Batch API: "On the Message Batches API, Claude Opus 5.5, Claude Opus 5, Claude Sonnet 5.5, ... support up to 300k output tokens with the output-300k-2026-03-24 beta header." Fable 5.1 is NOT in that list. Opus 5.5 model page: "Max output (Batch API, beta): 300K tokens" — [Opus 5.5 overview](https://platform.claude.com/docs/en/models/opus-5-5/overview)
- Tokenizer: "1M tokens is roughly 555k words or 2.5M Unicode characters on the current tokenizer (introduced with Claude Opus 4.7); models before it fit about 750k words in 1M tokens. 200k tokens is roughly 150k words." — [Models overview](https://platform.claude.com/docs/en/models/overview). Fable 5.1 uses "the same [tokenizer] as Claude Fable 5 (introduced with Claude Opus 4.7). Compared with models older than Claude Opus 4.7, the same text produces roughly 30% more tokens." — [What's new in Fable 5.1](https://platform.claude.com/docs/en/models/fable-5-1/whats-new-fable-5-1)
- Image/PDF cap: "A single request can include up to 600 images or PDF pages (100 for models with a 200k-token context window)." — [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)
- Overflow behavior: "If the input alone already exceeds the model's context window, the API returns a 400 `invalid_request_error` ('prompt is too long') on every model. On Claude 4.5 models and newer, if input tokens plus `max_tokens` exceeds the context window size, the API accepts the request. If generation then reaches the context window limit, it stops with `stop_reason: "model_context_window_exceeded"`." — [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)
- Fast mode (Opus 5.5 only of the two): "Fast mode pricing applies across the full context window, including requests over 200k input tokens." — [Pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Programmatic check: the Models API returns `max_input_tokens`, `max_tokens`, and a `capabilities` object per model — [Models overview](https://platform.claude.com/docs/en/models/overview)
- Corroboration/conflict note: third-party aggregators (haimaker.ai, llmgateway.io, cometapi) list 1M / 128K for Fable 5.1; one aggregator (aiindigo.com) claimed 200K for Mythos 5.1, which contradicts the official docs and should be disregarded.

### Inferences
- For a Claude Code plugin, the "advertised" cap for both models is 1,000,000 tokens with no economic cliff at 200K; any threshold logic that keyed off a 200K premium tier (as on older Sonnet 4.x 1M-beta models) is obsolete for these models.
- Because the current tokenizer yields ~30% more tokens per text than pre-Opus-4.7 models, a 1M window holds roughly the same text as ~770K tokens on the old tokenizer; heuristics calibrated in words/characters rather than tokens should be re-scaled.

### Gaps
- No official "effective context" figure (e.g., "performance holds to X tokens") is published for either model. See KQ3.

## KQ2. Pricing per million tokens: input, output, cache write (5m / 1h), cache read, multipliers

### Takeaway
Fable 5.1: $10 in / $50 out, cache write $12.50 (5m) / $20 (1h), cache read $0.25 (0.025x). Opus 5.5: $4 in / $20 out, cache write $5 (5m) / $8 (1h), cache read $0.20 (0.05x). Cache-write multipliers are 1.25x (5m) and 2x (1h) for all models; cache-read multipliers are model-specific (0.025x Fable/Mythos 5.1, 0.05x Opus/Sonnet 5.5, 0.1x everything else).

### Cited Findings
- Pricing table rows (USD / MTok, columns: base input | 5m cache write | 1h cache write | cache hits & refreshes | output):
  - Claude Fable 5.1: $10 | $12.50 | $20 | $0.25 | $50
  - Claude Mythos 5.1 (limited availability): $10 | $12.50 | $20 | $0.25 | $50
  - Claude Fable 5: $10 | $12.50 | $20 | $1 | $50
  - Claude Opus 5.5: $4 | $5 | $8 | $0.20 | $20
  - Claude Opus 5: $5 | $6.25 | $10 | $0.50 | $25
  — [Pricing](https://platform.claude.com/docs/en/about-claude/pricing); identical table on [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Multipliers: "5-minute cache write: 1.25x base input price ... 1-hour cache write: 2x base input price ... Cache read (hit): 0.1x base input price (0.025x on Claude Fable 5.1 and Claude Mythos 5.1; 0.05x on Claude Opus 5.5 and Claude Sonnet 5.5)". "On Claude Fable 5.1 and Claude Mythos 5.1, a cache hit costs 2.5% of the standard input price ($0.25 USD per million tokens). On Claude Opus 5.5 and Claude Sonnet 5.5, a cache hit costs 5% of the standard input price ($0.20 USD per million tokens on Claude Opus 5.5 ...)." "These multipliers stack with other pricing modifiers, including the Batch API discount and data residency." — [Pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Break-even: "caching pays off after one cache read for the 5-minute duration (1.25x write), or after two cache reads for the 1-hour duration (2x write)" (stated for the 0.1x case) — [Pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Batch API: 50% off; Fable 5.1 $5 / $25; Opus 5.5 $2 / $10 — [Pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Fast mode (Opus 5.5): $8 input / $40 output per MTok; "Prompt caching multipliers apply on top of fast mode pricing"; not available with Batch API; available on Claude API and Foundry (Azure-hosted), not on Bedrock/Claude Platform on AWS/Google Cloud — [Pricing](https://platform.claude.com/docs/en/about-claude/pricing); announcement says fast mode gives "up to 2.5x speed" — [Opus 5.5 announcement](https://www.anthropic.com/claude-opus-5-5)
- Data residency: "For Claude 4.6 and later models, specifying US-only inference through the `inference_geo` parameter incurs a 1.1x multiplier on all token pricing categories, including input tokens, output tokens, cache writes, and cache reads." — [Pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Fable 5.1 cache-read change: "Cache reads (hits and refreshes) cost 0.025 times the base input price on these models, compared with 0.05 on Claude Opus 5.5 and Claude Sonnet 5.5, and 0.1 on other Claude models. Long agentic sessions that re-read a cached prefix pay a quarter of the Claude Fable 5 rate." — [What's new in Fable 5.1](https://platform.claude.com/docs/en/models/fable-5-1/whats-new-fable-5-1); announcement: "Cache reads now cost 75% less, or $0.25 per million tokens" — [Fable/Mythos 5.1 announcement](https://www.anthropic.com/claude-fable-and-mythos-5-1)
- Opus 5.5 vs Opus 5: "$4 USD per million input tokens and $20 USD per million output tokens, below Claude Opus 5's $5 and $25, with 5-minute cache writes at $5, 1-hour cache writes at $8, and cache reads at $0.20 per million tokens (0.05x the base input price)." — [What's new in Opus 5.5](https://platform.claude.com/docs/en/models/opus-5-5/whats-new-opus-5-5); Anthropic says at default settings Opus 5.5 "will cost 40% less than Opus 5 on typical workloads" — [Opus 5.5 announcement](https://www.anthropic.com/claude-opus-5-5)
- Fable 5.1 vs Fable 5 cost: "will cost an estimated 25% less than Fable 5 for typical workloads" (estimate based on four weeks of August 2026 usage); "up to approximately 45%" savings on complex coding / highly agentic tasks — [Fable/Mythos 5.1 announcement](https://www.anthropic.com/claude-fable-and-mythos-5-1)
- Minimum cacheable prompt: 512 tokens on Fable 5.1, Mythos 5.1, Opus 5.5, Opus 5, Sonnet 5.5, Fable 5, Mythos 5, Haiku 5.5 (vs 1,024 on Opus 4.8 / Sonnet 5; 4,096 on Opus 4.6 / 4.5 / Haiku 4.5). "You can define up to 4 cache breakpoints." Lookback window: at most 20 blocks per breakpoint. — [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Cache-invalidation rules relevant to agents: changing top-level `output_config.effort` invalidates message caches; per-message effort (beta `mid-conversation-output-config-2026-07-01`) keeps the cache on Fable 5.1 and Opus 5.5; mid-conversation `role: "system"` messages don't invalidate system/message caches on Fable 5.1 / Opus 5.5; "Cache remains valid when only tool results are provided as user messages." — [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching); [Effort](https://platform.claude.com/docs/en/build-with-claude/effort)
- Measured cache economics (Anthropic): "Over a full day of real traffic, agent loops read a median 84% of their input from the cache, and the top 10% of them, coding or not, read 94% or more." "Deep in a task, a well-built loop pays full price on under 1% of its input." "Below about 80%, look for something breaking the cache." Breaking a 100,000-token prefix on Fable 5.1 / Mythos 5.1 "costs $1.25 USD against a $0.025 USD read" (50x). Task cost without caching vs with: Opus 5.5 on SWE-bench Pro 3.3x; Fable 5.1 on DeepResearch Bench II "$37.94 USD to $6.89 USD per task". — [Optimizing for cost and intelligence](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)
- Tool-use system prompt overhead: Opus 5.5 = 286 tokens (tool_choice auto/none). No Fable 5.1 row in that table. — [Pricing](https://platform.claude.com/docs/en/about-claude/pricing)

### Inferences
- Effective per-token cost of a warm cached prefix: Fable 5.1 $0.25/MTok vs Opus 5.5 $0.20/MTok — nearly equal in absolute terms despite the 2.5x base-price gap. A plugin's cost model should treat cache-read cost as the dominant steady-state input cost (per Anthropic's own measurement), and cache-write cost ($12.50 vs $5 per MTok at 5m) as the penalty for every cache break (compaction, system-prompt edit, effort change).
- Compaction economics flip on Fable 5.1: carrying a large cached context costs 2.5% of base per turn, while re-writing a post-compaction prefix costs 125% of base. Anthropic says explicitly that "compacting early to save cost may no longer be the right cost-intelligence tradeoff on Claude Fable 5.1" (see KQ3).

### Gaps
- No official per-token price for Mythos 5.1 beyond "shares Claude Fable 5.1's specifications and pricing" (same numbers as Fable 5.1).
- Fable 5.1 tool-use system-prompt token overhead is not published (not in the pricing table).

## KQ3. Official Anthropic statements on long-context performance, "effective context", recommended working size, or degradation at high fill

### Takeaway
Anthropic acknowledges context rot qualitatively in current docs ("As token count grows, accuracy and recall degrade") but publishes NO numeric "effective context" or recommended working-set size for Fable 5.1 or Opus 5.5. The only quantitative long-context evidence is the system cards' ProgramBench (long-context agentic coding, episodes "up to the full 1M token window"): Opus 5.5 91.2%, Fable 5.1 87.6%, Opus 5 85.4%. There is no needle-in-a-haystack or recall-vs-length curve in either system card.

### Cited Findings
- Current docs, qualitative: "A larger context window allows the model to handle more complex and lengthy prompts, but more context isn't automatically better. As token count grows, accuracy and recall degrade, a phenomenon known as *context rot*. This makes curating what's in context just as important as how much space is available." — [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)
- Compaction overview: compaction "keeps the active context small, because response quality degrades as a conversation grows." — [Compaction](https://platform.claude.com/docs/en/build-with-claude/compaction); threshold-compaction page: "as a conversation grows, response quality degrades" — [Compaction at a token threshold](https://platform.claude.com/docs/en/build-with-claude/compaction-threshold)
- `[STALE-RISK: published Sep 29, 2025, but still the doc that current pages link to for "why long contexts degrade"]` Context rot: "the model's ability to accurately recall information from that context decreases" as tokens increase; "attention budget"; "Context, therefore, must be treated as a finite resource with diminishing marginal returns"; "a performance gradient rather than a hard cliff". Guiding principle: "the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome." No numeric threshold given. — [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Fable 5.1 system card §8.11 "Long context" / §8.11.1 ProgramBench (pp. 175–176): "ProgramBench is a long-context agentic coding benchmark of 200 program reconstruction tasks. Given only a binary compiled from an open-source project and that project's documentation, the agent must rebuild a codebase ... On this set, Claude Fable 5.1 scored 87.6%, while Claude Opus 5 scored 85.4% and Fable 5 scored 86.3%. We believe ProgramBench is a strong measure of long-context coding performance: Fable 5.1 episodes cover a range of context lengths up to the full 1M token window, and the tasks test long-context capabilities that closely align with practical downstream use cases." Standard eval config: "adaptive thinking at max effort ... averaged over five trials. Context window sizes are evaluation dependent and do not exceed 1M tokens." — [Fable 5.1 & Mythos 5.1 System Card](https://www.anthropic.com/claude-fable-5-1-mythos-5-1-system-card) (PDF, 212 pages)
- Opus 5.5 system card §8.10 "Long context" / §8.10.1 ProgramBench (pp. 183–184): "Claude Opus 5.5 scored 91.2%, whereas Claude Fable 5.1 scored 87.6% and Claude Opus 5 scored 85.4%. ... Opus 5.5 episodes cover a range of context lengths up to the full 1M token window". Multi-agent ProgramBench note: "while the single-agent configuration presented in Section 8.10.1 used a 1M token budget, here we use context compaction and a 20M token budget". — [Opus 5.5 System Card](https://www.anthropic.com/claude-opus-5-5-system-card) (PDF, 230 pages)
- Both system cards flag long trajectories as an evaluation blind spot: "our automated behavioral audit currently has relatively thin coverage of multi-agent scenarios and tasks with very long trajectories" and "Very long trajectories — models may take many turns to be talked into misaligned actions, and context compaction can further change how models act. We simulate compaction, but we have more limited coverage of long trajectories." — [Fable 5.1 & Mythos 5.1 System Card](https://www.anthropic.com/claude-fable-5-1-mythos-5-1-system-card) (p. 90); same language in [Opus 5.5 System Card](https://www.anthropic.com/claude-opus-5-5-system-card)
- Fable 5.1 capability claims: "Long-context work, reasoning over and connecting details across the full 1M token context window" listed as one of six improvement areas; "Agentic coding over long sessions ... across sessions that run for hours." — [What's new in Fable 5.1](https://platform.claude.com/docs/en/models/fable-5-1/whats-new-fable-5-1)
- Announcement anecdotes (customer-reported, not Anthropic benchmarks): Fable 5.1 — Ramp "One unattended 38-hour run"; MongoDB "ran for hours unattended"; Shopify "more comfortable with long, unattended work than Fable 5". Opus 5.5 — Clio "stayed on task for over 18 hours". Neither announcement states a context-window size or any effective-context figure. — [Fable/Mythos 5.1 announcement](https://www.anthropic.com/claude-fable-and-mythos-5-1); [Opus 5.5 announcement](https://www.anthropic.com/claude-opus-5-5)
- Compaction-timing guidance specific to Fable 5.1: "Because cache reads are now cheaper ..., compacting early to save cost may no longer be the right cost-intelligence tradeoff on Claude Fable 5.1, so experiment with later compaction points." — [Prompting Claude Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1)
- Measured compaction/pruning effect on cost (not quality): on a long run "compaction saves 32% and pruning 39%"; on a short 20-issue run "context editing adds 73%" and "the levers saved little or nothing". "Make every cache-invalidating change at a natural break, such as the first request after a compaction." — [Optimizing for cost and intelligence](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)
- Claude Code docs: "Fable 'holds long sessions without losing the thread.'" (marketing-style, no number) — [Claude Code model config](https://code.claude.com/docs/en/model-config)

### Inferences
- Anthropic's own long-context benchmark (ProgramBench) is agentic coding across the full window, and both models score high there; Anthropic treats long-context capability as a strength rather than publishing a degradation curve. A plugin cannot cite an official "effective context" cut-off; any threshold (e.g., 60% / 80% of window) must be the plugin author's heuristic, and the notes should label it as such.
- The only official numeric anchors available for threshold tuning are (a) Claude Code's own default auto-compact point (~967K on native-1M models, see KQ6), (b) the API's threshold-compaction default (150,000 input tokens), and (c) the context-editing default trigger (100,000 input tokens). These are operational defaults, not performance-degradation points.

### Gaps
- No needle-in-a-haystack, RULER, or recall-vs-fill results for Fable 5.1 or Opus 5.5 in any Anthropic source found (0 "needle" hits in both system cards).
- No official statement of a "recommended working context size" or "degradation onset" token count. Anthropic publishes nothing on this; say so explicitly.
- The ProgramBench distribution of context lengths per episode is not published (only "up to the full 1M token window").

## KQ4. Fable 5.1 vs Opus 5.5 differences that matter for context management

### Takeaway
Both run adaptive thinking that cannot be disabled, default to `display: "omitted"`, keep ALL prior-turn thinking blocks in context (billed as input), and bind thinking blocks to the model and to the conversation prefix. Key differences: Fable 5.1 defaults to `high` effort, Opus 5.5 to `medium`; Opus 5.5 "tends to think more per turn" than Opus 5 at a given level; Fable 5.1 tends to issue one tool call per turn where Fable 5 batched, writes fewer progress updates, and rewrites whole files; Opus 5.5 is reported ~30% faster and uses fewer output tokens per task; thinking readability is asymmetric (Fable 5.1 can read Opus 5.5 blocks on the Claude API, Opus 5.5 cannot read Fable 5.1 blocks).

### Cited Findings
Thinking / effort defaults
- Table: Fable 5.1 "Thinking: Adaptive (always on)", "Default effort: `high`", "Comparative latency: Slower"; Opus 5.5 "Adaptive (always on)", "Default effort: `medium`", "Moderate". "Extended thinking is the manual thinking.type 'enabled' + budget_tokens mode on earlier models; it is deprecated on Claude Opus 4.6 and Claude Sonnet 4.6 and not accepted on later models." — [Models overview](https://platform.claude.com/docs/en/models/overview)
- Opus 5.5: "thinking is always on: a request that sets `thinking: {"type": "disabled"}`, or a manual budget with `thinking: {"type": "enabled", "budget_tokens": N}`, returns a 400 `invalid_request_error`." "More thinking per turn at a given effort level. At the same effort setting the model tends to think more per turn than Claude Opus 5, most of all at `xhigh` and `max`." — [What's new in Opus 5.5](https://platform.claude.com/docs/en/models/opus-5-5/whats-new-opus-5-5)
- Fable 5.1: "Adaptive thinking is always on. `thinking: {"type": "enabled"}` with `budget_tokens` and `thinking: {"type": "disabled"}` both return a 400 error." "`thinking.display` defaults to `"omitted"`. `"summarized"` is available, and the raw chain of thought is never returned." Prefill returns 400; non-default temperature/top_p/top_k return 400. — [What's new in Fable 5.1](https://platform.claude.com/docs/en/models/fable-5-1/whats-new-fable-5-1)
- Effort levels: `low`, `medium`, `high`, `xhigh`, `max` all supported on both. `xhigh` is described as for "Long-running agentic and coding tasks (over 30 minutes) with token budgets in the millions". "Effort is a behavioral signal, not a strict token budget." "Lower effort also means fewer and terser tool calls." — [Effort](https://platform.claude.com/docs/en/build-with-claude/effort)
- In Claude Code / apps: "Fable 5.1 defaults to High effort in Claude Code, and to Medium in Claude Cowork and on Claude.ai." — [Fable/Mythos 5.1 announcement](https://www.anthropic.com/claude-fable-and-mythos-5-1). Claude Code: Opus 5.5 default `medium`; `max` not accepted in `effortLevel`/`modelSettings` keys; `max` "may show diminishing returns and is prone to overthinking." — [Claude Code model config](https://code.claude.com/docs/en/model-config)
- Measured effort/cost (Opus 5.5, SWE-bench Pro subset, cost per task): `low` 87.4% / $0.11; `medium` 92.8% / $0.21; `high` 95.3% / $0.29; `xhigh` 96.7% / $0.74. Fable 5.1 DeepResearch Bench II: `low` 66% / $4.48; `high` 65% / $6.89 ("higher effort bought no score, only cost"). Long coding tasks: "`medium` cost about 30% to 52% less than `high`, and `low` about two thirds less," with up to 15 points lower accuracy. — [Optimizing for cost and intelligence](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)
- `max_tokens` guidance: Opus 5.5 — "For the long turns that agentic coding can produce, a `max_tokens` of 128,000, the model's maximum, has worked well in Anthropic's testing." — [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5). Fable 5.1 — "At `high` and above, set a large `max_tokens`. It's a hard limit on total output (thinking plus response text)." At `xhigh`/`max` it "can think for longer before it starts writing its reply" and "may draft much of that deliverable in its thinking and then write it out again as the reply". — [Effort](https://platform.claude.com/docs/en/build-with-claude/effort); [Prompting Claude Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1)

Output verbosity / token efficiency
- Opus 5.5: "generates output tokens more than 30 percent faster than Claude Opus 5 and tends to finish the same task with fewer tokens." "at its default `medium` effort the model matched or beat Claude Opus 5 at `high` effort on such tasks, in fewer steps and with fewer tokens." — [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5). Customer reports in the announcement: Box "40% less verbose without losing accuracy"; Factory "20 to 25% fewer output tokens at medium effort"; an early tester: Opus 5 "used 2.5x as many tokens" on a 200,000-line audit; internal HAProxy C-to-Rust test: Opus 5.5 cost 51% less than Fable 5.1. — [Opus 5.5 announcement](https://www.anthropic.com/claude-opus-5-5)
- Opus 5.5 multi-turn: "In multi-turn chat, Claude Opus 5.5 sometimes goes back over an earlier answer while it thinks about a new message, even a short follow-up, which adds thinking and latency on later turns." — [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)
- Fable 5.1 vs Fable 5: "Denser prose in places"; "Less formatting in chat"; "Whole-file rewrites for small changes ... the rewrite costs more output tokens and time"; "Fewer progress updates during long tool runs." The extra turns cost tokens, round trips, and wall-clock time but don't reduce answer quality." Fix: one-line batching nudge appended as a turn-scoped system message. Thinking blocks across turns

### Inferences
- Context growth per turn on both models = text + tool calls + tool results + ALL thinking (current and prior turns). Since Fable 5.1 defaults to `high` and Opus 5.5 to `medium` but "thinks more per turn" than Opus 5, neither has a structurally smaller thinking footprint; a plugin should measure actual `usage` rather than assume Opus 5.5 is lighter.
- Because neither model receives the API's injected token-budget warnings and task budgets are unsupported in Claude Code, Claude Code sessions on these models have no model-visible context-remaining signal unless the harness/plugin provides one (e.g., in a status line or hook output).
- A classifier fallback to Opus 4.8/5 mid-session drops Fable 5.1's thinking blocks for those turns (unreadable by the fallback model). This is an additional context-continuity hazard specific to Fable 5.1 coding sessions.

### Gaps
- No published typical thinking-token counts per effort level for either model (Anthropic publishes per-task cost, not token distributions).
- No official verbosity measurement (tokens per task) for Fable 5.1 vs Opus 5.5 beyond customer anecdotes and the single HAProxy internal test.

## KQ5. What counts toward the context window in agentic loops (tool results, thinking, cached prefix)

### Takeaway
Everything in the request counts: system prompt, tool definitions, every message (including tool results, images, documents), prior-turn thinking blocks on these models, and the current turn's output including thinking. Prompt caching changes what you pay, not what counts: `input_tokens + cache_read_input_tokens + cache_creation_input_tokens` all occupy the window.

### Cited Findings
- "Everything in the request counts toward the context window: the system prompt, every message in `messages` (including tool results, images, and documents), and your tool definitions. The output Claude generates for the turn, including its extended thinking, counts too. Every response reports what the request consumed in its `usage` field. If you use prompt caching, the input count is split across `input_tokens`, `cache_read_input_tokens`, and `cache_creation_input_tokens`, and all three count toward the window." — [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)
- "Cached prompt prefixes still occupy the context window: prompt caching changes what you pay for those tokens, not whether they count." — [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)
- Thinking: "Thinking tokens are a subset of your `max_tokens` parameter, are billed as output tokens, and count toward rate limits." On keep-all models (Fable 5.1, Opus 5.5), "the API keeps previous thinking blocks by default, and they count toward the context window like any other input tokens." "Thinking tokens are billed as output tokens once, when they are generated. On models that keep previous thinking blocks, the kept blocks are then part of later requests' input and are billed as input tokens." — [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)
- Tool-use round trip: "You must return the thinking block with the corresponding tool results. This is the only case where you have to return thinking blocks." "All input and output components count toward the context window." — [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)
- Dropped (unreadable or pruned) thinking blocks: "Dropped blocks don't count toward `input_tokens` and aren't billed." — [What's new in Fable 5.1](https://platform.claude.com/docs/en/models/fable-5-1/whats-new-fable-5-1); API "bills input tokens only for the blocks actually shown to Claude" — [Thinking](https://platform.claude.com/docs/en/build-with-claude/thinking)
- Cleared turn-scoped system messages: "a cleared message costs no input tokens" (beta `mid-conversation-system-clear-at-2026-08-21`) — [What's new in Fable 5.1](https://platform.claude.com/docs/en/models/fable-5-1/whats-new-fable-5-1)
- Tool definitions overhead: the `tools` parameter, `tool_use` blocks, and `tool_result` blocks all count; plus a per-model tool-use system prompt (Opus 5.5: 286 tokens). Deferred tool loading via the tool search tool reduces it. — [Pricing](https://platform.claude.com/docs/en/about-claude/pricing); [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)
- Server-side context management primitives and their numeric defaults:
  - Threshold compaction (beta `compact-2026-01-12`, strategy `compact_20260112`): default trigger `{"type": "input_tokens", "value": 150000}`; "`value` must be at least 50,000 tokens"; no maximum stated; supported on Fable 5.1 and Opus 5.5; "The API automatically drops all content blocks prior to the `compaction` block"; on Claude 5.1+ "thinking blocks from before a `compaction` block aren't carried forward, so the summary is all the model has of that earlier work." — [Compaction at a token threshold](https://platform.claude.com/docs/en/build-with-claude/compaction-threshold)
  - Compaction on demand (beta `compact-2026-09-04`, top-level `compaction` parameter): you choose when; can run in background; kept turns can keep thinking under conditions. — [What's new in Opus 5.5](https://platform.claude.com/docs/en/models/opus-5-5/whats-new-opus-5-5); [Compaction](https://platform.claude.com/docs/en/build-with-claude/compaction)
  - Context editing (beta `context-management-2025-06-27` `[STALE-RISK: 2025 header, still current]`): `clear_tool_uses_20250919` default trigger 100,000 input tokens, default `keep` 3 tool uses, `clear_at_least` None, `exclude_tools` None, `clear_tool_inputs` false; "Invalidates cached prompt prefixes when content is cleared." `clear_thinking_20251015` default keep = all turns on Fable/Mythos and Opus 4.5+; must be listed first in `edits`. On Fable 5.1 / Opus 5.5 "server-side context management never invalidates thinking blocks." — [Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Task-budget accounting (for comparison with window accounting): the budget counts "what Claude sees ... not what's in your request payload" — resent history is not re-counted, only new tool results and generated tokens. — [Task budgets](https://platform.claude.com/docs/en/build-with-claude/task-budgets)

### Inferences
- For a context-health gauge, the correct "fill" number per request is `input_tokens + cache_read_input_tokens + cache_creation_input_tokens + output_tokens` from `usage` (the last term includes thinking); cache reads must not be subtracted.
- The API's own operational defaults (compaction at 150K input tokens; tool-result clearing at 100K) are set an order of magnitude below the 1M window; they reflect Anthropic's cost/quality tuning for generic agents, not a hard capability limit.

### Gaps
- Anthropic does not publish how much of a typical Claude Code turn's growth is thinking vs tool results for these models.

## KQ6. Claude Code-specific context facts (operational defaults a plugin must respect)

### Takeaway
In Claude Code, Fable 5.1 and Opus 5.5 run at 1M by default; auto-compaction on native-1M models fires at about 967K tokens unless overridden (`/autocompact`, `autoCompactWindow`, `--autocompact`, or `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, range 100K–1M). `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` forces a 200K window (compact at 200K). Opus 5.5 is the default model on Pro/Max/Team/Enterprise/API; Fable must be selected explicitly.

### Cited Findings
- Default model: "Pro, Max, Team, Enterprise, and Anthropic API: Opus 5.5"; "Fable models are not the default on any plan or provider. You select them explicitly with `/model fable` or `claude --model fable`." Alias history: v2.1.280 `opus` → Opus 5.5; v2.1.257 `fable` → Fable 5.1. — [Claude Code model config](https://code.claude.com/docs/en/model-config)
- 1M default: "Fable 5.1, Fable 5, Sonnet 5 and later, Haiku 5.5, and Opus 4.7 and later run with the 1M window by default, with no `[1m]` suffix needed." Pricing in Claude Code: "standard pricing with no premium above 200K", except Haiku 5.5 over 100K. — [Claude Code model config](https://code.claude.com/docs/en/model-config)
- Default auto-compact thresholds (verbatim): "If you don't set an auto-compact window, Claude Code compacts when the conversation reaches the model's context limit, except in these sessions: ... Models running with a native 1M window compact before the window fills, at about 967K tokens by default. These include the Fable models, Sonnet 5 and later, Haiku 5.5, and Opus 4.7 and later. ... Sessions on a model ID Claude Code doesn't recognize, such as an LLM gateway alias, compact at the context window Claude Code assumes for the ID". Unrecognized IDs are assumed 200K; override with `CLAUDE_CODE_MAX_CONTEXT_TOKENS` or `modelOverrides`. — [Claude Code model config](https://code.claude.com/docs/en/model-config)
- Setting the window: `/autocompact <value>` (saved per model under `modelSettings` since v2.1.288; `/autocompact auto` restores the tuned default); `autoCompactWindow` setting (every model); `--autocompact` flag (one launch); `CLAUDE_CODE_AUTO_COMPACT_WINDOW` env var (plain token count; "takes precedence over the command, the flag, and the setting"). "The command and the flag accept a window size from 100K to 1M tokens" (`200000`, `500k`, `1M`, or bare `200` = 200,000). "Claude Code caps the window at the model's context window." Related: `autoCompactEnabled`, `idleCompaction`, `DISABLE_COMPACT`. — [Claude Code model config](https://code.claude.com/docs/en/model-config); [Claude Code settings reference](https://code.claude.com/docs/en/settings-reference)
- Turning 1M off: "`CLAUDE_CODE_DISABLE_1M_CONTEXT=1` ... also treats the model as having a 200K context window"; with auto-compaction on, sessions compact at 200K; with it off, sessions stop with the context-limit error. — [Claude Code model config](https://code.claude.com/docs/en/model-config)
- What survives compaction: "As of v2.1.198, the summarization request inherits your session's extended thinking configuration"; "Right after compaction, Claude Code re-reads up to five of the files Claude has read or edited in the session, choosing the ones modified most recently. A file over 5,000 tokens comes back as a path reference without its content"; skill bodies re-injected "capped at 5,000 tokens per skill"; skill descriptions are not re-injected; path-scoped rules and nested CLAUDE.md are summarized away; SessionStart hooks matching the `compact` source re-run. — [Claude Code context window](https://code.claude.com/docs/en/context-window)
- Startup context items (from the official interactive walkthrough): auto memory loads "The first 200 lines or 25KB, whichever comes first"; MCP tool schemas stay deferred by default, `ENABLE_TOOL_SEARCH=auto` loads them upfront "when they fit within 10% of the context window". — [Claude Code context window](https://code.claude.com/docs/en/context-window)
- Manual levers: `/compact <focus>`, `/rewind` → "Summarize from here / up to here", `/autocompact 500k` to "Compact earlier". — [Claude Code context window](https://code.claude.com/docs/en/context-window)
- Effort in Claude Code: `effortLevel` (`low`/`medium`/`high`/`xhigh`; `max` not accepted), `maxEffortLevel` cap (v2.1.267+), `CLAUDE_CODE_EFFORT_LEVEL` env, `/effort`; `alwaysThinkingEnabled` (thinking on by default); `MAX_THINKING_TOKENS=0` turns thinking off for a session "On adaptive-reasoning models the number itself is ignored" (note: the API rejects thinking-off on Fable 5.1 / Opus 5.5, so this is effectively inapplicable to them). — [Claude Code settings reference](https://code.claude.com/docs/en/settings-reference)
- Prompt-cache controls: `DISABLE_PROMPT_CACHING`, `DISABLE_PROMPT_CACHING_OPUS`, `DISABLE_PROMPT_CACHING_FABLE`; `promptCacheTtl` and `subagentPromptCacheTtl` settings. — [Claude Code model config](https://code.claude.com/docs/en/model-config); [Claude Code settings reference](https://code.claude.com/docs/en/settings-reference)
- Third-party reports (not official; included only as a signal that real-world compaction points deviate from docs): GitHub issues report auto-compact firing at ~420K, ~367K (Opus 4.7 [1m], CC 2.1.119), and ~76K (Opus 4.6 1M) on 1M models; one guide claims an ~83.5% trigger. These conflict with the official "about 967K" statement and are version-specific; treat as unverified. — [claudeissues #40757](https://claudeissues.com/issue/40757-auto-compact-triggers-at-420k-tokens-despite-opus-having-1m-context-window-thres); [claudeissues #54056](https://claudeissues.com/issue/54056-bug-auto-compact-triggers-consistently-at-367k-tokens-on-opus-4-7-1m-in-claude-c); [claudefa.st](https://claudefa.st/blog/guide/mechanics/context-buffer-management)

### Inferences
- A context-health plugin should read the effective window from the running configuration (model ID → 1M for Fable 5.1 / Opus 5.5; 200K if `CLAUDE_CODE_DISABLE_1M_CONTEXT=1`; `CLAUDE_CODE_MAX_CONTEXT_TOKENS` if set; unrecognized gateway IDs → 200K) and the effective auto-compact point from `CLAUDE_CODE_AUTO_COMPACT_WINDOW` > `--autocompact` > per-model `modelSettings.autoCompactWindow` > `autoCompactWindow` > default (~967K on native-1M).
- Any plugin "yellow/orange/red" zones expressed as absolute tokens calibrated for 200K sessions (e.g., 200–300K) are below 30% of a 1M window and would fire constantly on Fable 5.1 / Opus 5.5; zones should be expressed as a fraction of the effective auto-compact window, with the caveat (KQ3) that no official degradation curve justifies any particular fraction.

### Gaps
- The exact percentage behind "about 967K" and whether it is model-specific is not stated.
- The Claude Code docs do not describe the UI's "context left" warning thresholds (if any) numerically.
- `code.claude.com/docs/en/env-vars` was not fetched; exact description text for `CLAUDE_CODE_AUTO_COMPACT_WINDOW` / `CLAUDE_CODE_MAX_CONTEXT_TOKENS` there was not captured (behavior captured from model-config page).
