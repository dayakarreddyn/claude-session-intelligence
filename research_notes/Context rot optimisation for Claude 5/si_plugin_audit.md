## Key question 1 — What does the token budget measure, what are the zones, and how do adaptive zones work?

### Takeaway
SI tracks two different "token" quantities and mixes them: (a) a **cumulative tool-I/O estimate** (chars/4 + 100 per tool call, summed across the whole session) that is what gets stamped on every compact record, every session's `peak_tokens`, and the compact-history file that adaptive zones learn from; and (b) a **per-call context size** read from the transcript's latest assistant `usage` block (`input + cache_creation + cache_read`), which is what the zone-crossing hook and the statusline actually compare against the thresholds. Thresholds are fixed absolute token counts (200k/300k/400k) regardless of model, and because the adaptive-zone learner is fed cumulative numbers (p50 ≈ 1.4–1.6M) it is permanently pinned at its +30% clamp ceilings in practice (yellow 310k / orange 390k / red 520k; 263k / 343k when cost-tightened).

### Inferences
- Three telemetry fields share the name "tokens" but not the unit: `compacts.tokens`, `compact-history.tokens` and `sessions.peak_tokens` are cumulative tool-I/O estimates; `zone_transitions.tokens` and the statusline bar are per-call context size (except when the transcript read fails). The `/si stats` "COMPACTS Tokens p50 1.58M" line therefore does not describe context size at compact.
- Because the learner is fed cumulative numbers, `round(p50*0.9)` is always ≫ the 390k clamp, so `orange` is pinned at 390k (343k when cost-tightened by ×0.88 — matching the observed orange minimum 343,453), `yellow = orange - 80k` lands at 310k or 263k (matching the observed yellow minimum 263,252), and `red = min(520k, p90*1.1)` pins at 520k (matching the 44 red crossings in the 450–530k bucket with a minimum of 520,055). The "learning loop" is effectively a constant +30% widening of the static zones.
- The 23 red crossings above 1M (27% of 90d reds) are artifacts of the estimate fallback (confirmed 13/13 in the logs); they also explain the 25 `green → red` jumps (a transcript read fails, the cumulative estimate is in the millions, the zone jumps to red, then "zone descended" re-arms when the transcript read succeeds). The stats verdict "sessions are routinely pushing past the recommended compact line" is partly measuring this artifact. The 512 KB tail scan in `readTranscriptTokens` is the likely trigger (a single tool result larger than 512 KB pushes the last `usage` line out of the window).
- The token-budget hook's own `[TokenBudget] ~Xk tokens` messages (stderr, exit 0, so not model-visible) and the suggest-compact callouts (exit 2, model-visible) can report different zones for the same moment because they use different units.

### Gaps
- No field anywhere records context-fill % at compact time (what fraction of the model's window was in use when compaction fired). The data cannot say at what context size auto-compacts actually occur.
- Whether Claude Code's PreCompact payload exposes the pre-compact context size was not checked (the hook reads only `trigger`, `cwd`, `session_id`, `transcript_path` — [hooks/si-pre-compact.js:360-361](file:///Users/0xd/DWS/claude-session-intelligence/plugins/session-intelligence/hooks/si-pre-compact.js), [hooks/si-pre-compact.js:697](file:///Users/0xd/DWS/claude-session-intelligence/plugins/session-intelligence/hooks/si-pre-compact.js), [hooks/si-pre-compact.js:750](file:///Users/0xd/DWS/claude-session-intelligence/plugins/session-intelligence/hooks/si-pre-compact.js)).

## Key question 3 — What fires at zone crossings, at PreCompact, and at SessionStart after a compact?

### Takeaway
At a zone crossing (yellow, orange or red; crossings only, re-fire disabled by default) `si-suggest-compact.js` writes an advisory callout to stderr and exits 2 so Claude Code surfaces it to the model without blocking the tool; with the default `compact.stablePrefix: true` the headline omits the token count and cost ("Drift zone. Advisory only…"). At PreCompact the hook streams a markdown block to stdout (session-context hints, observed HOT/COLD shape, memory-offload, priorities review, memory cleanup, git-nexus note, a tip, up to six recallable archive ids, and a "NEXT (to resume)" footer), records the compact, writes a regret snapshot and a one-shot handoff file. SessionStart after a compact replays that handoff as `additionalContext` plus a `systemMessage` banner, with a once-a-day memory-hygiene reminder.

### Cited Findings

## Key question 7 — Gap list: what a model-aware, rot-aware design would need that SI lacks

### Takeaway
SI's current mechanics are directory-shaped, absolute-token, model-agnostic advisories layered on a telemetry base whose core "tokens" metric mixes cumulative tool I/O with per-call context size. A model-aware, rot-aware redesign would need to (1) measure context-fill % against the real window, (2) stop learning thresholds from cumulative numbers, (3) eliminate the estimate-fallback artifacts, (4) act on stale tool output rather than archive it, (5) make the model-visible callout quantitative again, (6) time compaction against cache economics, (7) use subagent data as an input, and (8) check summary quality after the fact.

### Inferences
Each gap below is tied to the finding above it.
1. **Context-fill % as the primary metric.** Replace the absolute zones with fractions of `contextCap` (already derivable from Claude Code's `context_window.context_window_size` per the statusline) so the same config means the same thing on a 200k and a 1M model, and record fill % on every compact row so auto vs manual compaction points become measurable.
2. **Fix the learner's input.** Adaptive zones should learn from per-call context size at compact (or fill %), not the cumulative tool-I/O estimate; today the ±30% clamp is doing all the work and the "learning loop" is a constant widening to 310k/390k/520k.
3. **Remove the estimate fallback from zone decisions** (or bound it to the cap): the fallback manufactures red crossings in the millions, inflates the red share, and produces `green→red` jumps; widening the transcript tail scan beyond 512 KB or caching the last known `usage` would remove the trigger.
4. **Stale-tool-output pruning advice.** SI already knows the id, size, tool and preview of every ≥4 KB result and which directories went COLD; a rot-aware PreCompact block could name the specific large results (by tool + path + size) that are safe to summarise or drop, and the model-visible callout could do the same mid-session, instead of relying on a 0%-used recall CLI.
5. **Put numbers back in the model-visible callout** (fill %, tokens, cost, cap) or make `stablePrefix` conditional on a demonstrated cache win; the drift log shows the prefix is not stable anyway.
6. **Cache-TTL-aware timing.** Use the per-turn `cacheHit` / `cacheTokens` SI already computes plus wall-clock gaps to advise compaction when the warm prefix is about to expire (or has just expired) rather than mid-burst, and persist cache-hit series so the advice can be evaluated.
7. **Subagent delegation as a first-class lever.** Feed agent return sizes and the agent share of spend into the zone diagnosis ("the last 3 Agent returns added ~N tokens"), and promote the delegation tip from a rotating one-liner to a concrete prompt when large reads/greps are detected in the shape log.
8. **Summary-quality checks.** After the handoff is consumed, compare the post-compact context size to the pre-compact size and the regret window outcome, and record both; today `continuationQuality` only says whether work landed in HOT vs DROP directories.
9. **Escalation path.** Given advisories did not prevent auto-compacts in the marathon sessions, a model-aware design needs a stronger step (periodic re-fire by fill %, or a directive rather than advisory at red) and a measurement of whether the model acted.
10. **Telemetry hygiene.** Reconcile JSONL and DB counts, store a single canonical `project` key per sid, fix the compact `Total cost` aggregation, and price background-agent rows before relying on the agent share.

### Gaps
- Whether Claude Code exposes the live context size to PreCompact or PostToolUse payloads (which would make item 1 trivial) was not verified in this audit; only the statusline stdin field is referenced in the code.
- The audit cannot quantify quality degradation at any token level from SI's data — SI records no outcome metric (task success, re-work, user corrections) that could be correlated with context size.
