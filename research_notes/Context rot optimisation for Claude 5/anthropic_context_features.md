# Anthropic context-engineering features (as of October 2026) and their reachability from a hooks-only Claude Code plugin

Research date: 2026-10-19. Doc pages on platform.claude.com and code.claude.com carry no explicit "last updated" date; where a page's own content pins its currency (beta header dates, "accounts created on or after August 31, 2026", Claude Code version numbers up to v2.1.303) I note it. Claude Code CHANGELOG head at fetch time: `## 2.1.303`. Note: `docs.claude.com` now 302-redirects API pages to `platform.claude.com/docs/en/...` and Claude Code pages to `code.claude.com/docs/en/...`; `anthropic.com/engineering` and `anthropic.com/news` 308-redirect some posts to `claude.com/blog/...` / `claude.dev/blog/...`.

Verdict vocabulary used below:
- **AUTO** = available in Claude Code sessions automatically
- **CONFIG(<key>)** = configurable in Claude Code via the named setting / env var / command
- **API-ONLY** = Messages API feature not reachable from a plugin that has only hooks + statusline
- **HOOK(<approach>)** = replicable (fully or partially) by a hook

## Key Question 1: Context editing API (`clear_tool_uses` / `clear_thinking`) and whether Claude Code uses it

### Takeaway
Context editing is a server-side, beta Messages API feature (`anthropic-beta: context-management-2025-06-27`) with two strategies, `clear_tool_uses_20250919` (default trigger 100,000 input tokens, keep 3 tool uses) and `clear_thinking_20251015`. There is no public Anthropic statement that Claude Code sends `context_management`; Claude Code's own docs describe a client-side equivalent ("It clears older tool outputs first, then summarizes the conversation if needed"). Verdict: the API strategies are **API-ONLY**; the behaviour is **AUTO** in Claude Code via its own client-side tool-result clearing and compaction, and partially **HOOK(PostToolUse `updatedToolOutput`)** for shrinking results before they enter context.

### Cited Findings
- Launch: "automatically clears stale tool calls and results from within the context window"; "combining the memory tool with context editing improved performance by 39% over baseline"; context editing alone 29%; in a 100-turn web search evaluation "reducing token consumption by 84%"; "available today in public beta on the Claude Developer Platform"; tied to Claude Sonnet 4.5. Published September 29, 2025 — [Anthropic, "Managing context on the Claude Developer Platform"](https://claude.com/blog/context-management)
- Beta header: `context-management-2025-06-27`, sent as `anthropic-beta` (or `betas=[...]` in SDKs) — [Context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Strategy `clear_tool_uses_20250919` parameters (verbatim defaults/descriptions): `trigger` default `100,000 input tokens` — "Once the prompt exceeds this threshold, clearing begins. You can specify this value in either `input_tokens` or `tool_uses`."; `keep` default `3 tool uses` — "Defines how many recent tool use/result pairs to keep after clearing occurs. The API removes the oldest tool interactions first."; `clear_at_least` default none — "If the API can't clear at least the specified amount, the strategy will not be applied."; `exclude_tools` default none — "List of tool names whose tool uses and results should never be cleared."; `clear_tool_inputs` default `false` — "Controls whether the tool call parameters are cleared along with the tool results." Cleared results are replaced with placeholder text. Example config in docs: `"trigger": {"type": "input_tokens", "value": 30000}`, `"keep": {"type": "tool_uses", "value": 3}`, `"clear_at_least": {"type": "input_tokens", "value": 5000}`, `"exclude_tools": ["web_search"]` — [Context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Strategy `clear_thinking_20251015`: `keep` accepts `{type: "thinking_turns", value: N}` ("N must be > 0") or `"all"`; default is model-specific (Opus 4.5+ keep all, Opus 4.1 and earlier last turn; Sonnet 4.6+ keep all, Sonnet 4.5 and earlier last turn; Haiku 5.5+ keep all, Haiku 4.5 and earlier last turn; Fable/Mythos all turns). "If your code runs across multiple model tiers, set `keep` explicitly rather than relying on the per-model default." When combined with tool clearing, "the `clear_thinking_20251015` strategy must be listed first in the `edits` array." — [Context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Server-side semantics: "Context editing is applied server-side before the prompt reaches Claude. Your client application maintains the full, unmodified conversation history." — [Context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Models: "Context editing is available on all supported Claude models." — [Context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Prompt-cache interaction: tool result clearing "Invalidates cached prompt prefixes when content is cleared... Use the `clear_at_least` parameter to ensure a minimum number of tokens is cleared each time."; thinking clearing: "When thinking blocks are **kept** in context (not cleared), the prompt cache is preserved... When thinking blocks are **cleared**, the cache is invalidated at the point where clearing occurs." — [Context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Response fields: non-streaming `context_management.applied_edits[]` with entries like `{"type": "clear_thinking_20251015", "cleared_thinking_turns": 3, "cleared_input_tokens": 15000}` and `{"type": "clear_tool_uses_20250919", "cleared_tool_uses": 8, "cleared_input_tokens": 50000}`; streaming: "the `context_management.applied_edits` field is included in the final `message_delta` event." `/v1/messages/count_tokens` accepts `context_management` and returns `input_tokens` (after clearing) plus `context_management.original_input_tokens` — [Context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Memory-tool coupling: "When your conversation context approaches the configured clearing threshold, Claude receives an automatic warning to preserve important information." — [Context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Client-side SDK `compaction_control` (TypeScript/Ruby `tool_runner` only): params `enabled` (required), `context_token_threshold` (default `100,000`), `model` (default same as main), `summary_prompt`; token calc `input_tokens + cache_creation_input_tokens + cache_read_input_tokens + output_tokens`; now **deprecated**: "The `compaction_control` parameter is deprecated in the TypeScript and Ruby SDKs and will be removed in a future version... The Python SDK removed it in v1.0."; "Anthropic recommends server-side compaction over SDK compaction." — [Context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Preserved-thinking caveat (Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5): "server-side context management never invalidates thinking blocks. Client-side edits to earlier turns can invalidate the thinking blocks in every later assistant turn. For new accounts created on or after August 31, 2026, a request that replays an invalidated block is rejected unless you opt into dropping it." — [Context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Claude Code's own client-side behaviour (official): "Claude Code manages context automatically as you approach the limit. It clears older tool outputs first, then summarizes the conversation if needed. Your requests and key code snippets are preserved; detailed instructions from early in the conversation may be lost." — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- Claude Code counts its own tool-result clearing as an "expected rebuild" cache miss: `Prompt cache (main): ... 1 expected rebuild (compaction or tool-result clearing) ...`; "when Claude Code has itself just rewritten the conversation, by [compaction] or by clearing old tool results from context, it counts the same kind of miss as an expected rebuild instead." (requires v2.1.251+) — [Manage costs](https://code.claude.com/docs/en/costs)
- Claude Code changelog `## 2.1.50`: "Improved memory usage during long sessions by clearing large tool results after they have been processed" (this is process memory, not context) — [CHANGELOG.md](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- A user-filed issue claims Claude Code v2.1.32 with Opus 4.6 stopped clearing tool results and speculates it had been using the Context Editing API; unverified, closed — [claudeissues.com #25666](https://claudeissues.com/issue/25666-context-editing-tool-result-clearing-regression-dynamic-context-management-lost)
- The context-editing docs page contains no mention of "Claude Code" or "Agent SDK" (only SDK tool runners and the `ant` CLI) — [Context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)

### Inferences
- Claude Code implements tool-result clearing and summarization client-side (it rewrites the request it sends, which is why it classifies the resulting cache miss as an "expected rebuild"); the API's `clear_tool_uses_20250919` operates server-side and leaves the client history intact, so the two are distinct mechanisms even though the effect is similar.
- Because the API strategy requires a request parameter and beta header, a hooks-only plugin cannot enable it. The closest hook-side lever is PostToolUse `hookSpecificOutput.updatedToolOutput` (replace a tool result before it enters context) and PreToolUse `updatedInput` (make the tool produce less output), both documented in Key Question 6.

### Gaps
- No Anthropic statement, in docs, blog, or changelog, confirms or denies that Claude Code sends `context_management` edits to the API. The "clears older tool outputs first" sentence is the only official description of its tool-result clearing, and it gives no threshold, keep-count, or placeholder text.
- The context-editing page's "Limitations" section was truncated in retrieval (final ~5 KB unread).

## Key Question 2: Server-side compaction (2026) — names, thresholds, and whether Claude Code uses it

### Takeaway
Two beta API variants exist: threshold compaction (`compact_20260112` edit under `context_management.edits`, header `compact-2026-01-12`, default trigger 150,000 input tokens, minimum 50,000) and on-demand compaction (top-level `"compaction": {"type": "summarize"}`, header `compact-2026-09-04`), with Anthropic now saying "Use on-demand compaction wherever it is available." Claude Code does **not** document using either; it runs its own summarization request client-side ("built on Claude Code's compact slash command"), configurable via `autoCompactWindow`, `/autocompact`, `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`, `DISABLE_AUTO_COMPACT`, `idleCompaction`, and observable/blockable via `PreCompact`/`PostCompact` hooks. Verdict: API compaction **API-ONLY**; Claude Code compaction **AUTO** + **CONFIG** + **HOOK(PreCompact/PostCompact/SessionStart `compact`)**.

### Cited Findings
**API: overview**
- "Compaction replaces the older turns of a conversation with a summary that Claude writes on the server, so you need no summarization code of your own. It keeps a long conversation or agent task inside the context window, and it keeps the active context small, because response quality degrades as a conversation grows." "Use on-demand compaction wherever it is available." Both variants are "in beta". — [Compaction overview](https://platform.claude.com/docs/en/build-with-claude/compaction)
- Comparison table: threshold compaction "runs inside the request that reaches the threshold", on-demand "Runs in the background: Yes"; kept turns keep their thinking only in on-demand mode under stated conditions. — [Compaction overview](https://platform.claude.com/docs/en/build-with-claude/compaction)

**API: threshold compaction (`compact_20260112`)**

- `trigger` default `{"type": "input_tokens", "value": 150000}`; "`input_tokens` is the only supported trigger type. `value` must be at least 50,000 tokens." — [Compaction at a token threshold](https://platform.claude.com/docs/en/build-with-claude/compaction-threshold)
- `pause_after_compaction` boolean, default `false`: "When enabled, the API returns a message with the `compaction` stop reason after generating the compaction block" — [Compaction at a token threshold](https://platform.claude.com/docs/en/build-with-claude/compaction-threshold)
- `instructions` string, default `null`: "Custom summarization prompt. - Supported models: claude-fable-5-1, claude-mythos-5-1, claude-fable-5, claude-mythos-5, claude-mythos-preview, claude-opus-5-5, claude-opus-5, claude-opus-4-8, claude-opus-4-7, claude-opus-4-6, claude-sonnet-5-5, claude-sonnet-5, claude-sonnet-4-6, claude-haiku-5-5; platforms Claude API, Claude Platform on AWS, Amazon Bedrock, Google Cloud, Microsoft Foundry (all "beta") — [Compaction at a token threshold](https://platform.claude.com/docs/en/build-with-claude/compaction-threshold)

### Inferences
- The identifiers `compact_20260112` / `compact-2026-01-12` and `compact-2026-09-04` date the two API variants to 12 Jan 2026 and 4 Sep 2026 respectively (Anthropic's naming convention embeds the release date); third-party posts tie the January launch to Opus 4.6 (5 Feb 2026) but I found no official date statement.
- Claude Code's compaction is architecturally the client-side "fork" pattern (same prefix + summarization user message), not the API `compaction` block. Nothing in the Claude Code docs, changelog, or the April 2026 engineering post says Claude Code switched to the server-side feature.
- For a plugin, the practical levers are: lower the window (`CLAUDE_CODE_AUTO_COMPACT_WINDOW` via `CLAUDE_ENV_FILE` from a SessionStart hook is not documented as affecting the running process; the env var must be set in the environment that starts Claude Code), steer the summary (CLAUDE.md compact instructions), re-inject state after compaction (SessionStart `compact`), veto a compaction (PreCompact exit 2), and read the result (PostCompact `compact_summary`).

### Gaps
- No official page states the dates on which `compact-2026-01-12` or `compact-2026-09-04` went live, nor whether Claude Code (any version) uses either.
- The default summarization prompt text for the API compaction is not published in the fetched portion (threshold page truncated at ~100 KB of 118 KB).
- Claude Code's exact default auto-compact percentage when a window is set (the "default percentage" that `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` cannot exceed) is not documented; third parties claim ~83–95%, unverified.

## Key Question 3: Memory tool (`memory_20250818`) and its relation to Claude Code auto-memory

### Takeaway
The API memory tool is client-side (`{"type": "memory_20250818", "name": "memory"}`, no beta header, Claude 4+), gives Claude six file commands under a `/memories` prefix, and the API auto-injects a "MEMORY PROTOCOL ... ASSUME INTERRUPTION" system instruction. Claude Code's auto-memory is a separate, Claude Code-side feature (files under `~/.claude/projects/<project>/memory/`, `MEMORY.md` index, first 200 lines or 25 KB loaded per session) and the docs never link it to `memory_20250818`. Verdict: API memory tool **API-ONLY**; Claude Code auto-memory **AUTO**, **CONFIG(`autoMemoryEnabled`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY`)**, and **HOOK(Stop/PostToolUse/PreCompact writing to memory files, SessionStart re-injecting)**.

### Cited Findings

## Key Question 4: Prompt caching — TTLs, pricing, breakpoints, invalidation, and prefix-stability guidance (API and Claude Code)

### Takeaway
API: `cache_control: {"type": "ephemeral"}` (5-minute default) or `{"type": "ephemeral", "ttl": "1h"}`; writes cost 1.25x (5m) / 2x (1h) base input, reads 0.1x (0.025x on Fable 5.1/Mythos 5.1, 0.05x on Opus 5.5/Sonnet 5.5); up to 4 breakpoints, 20-block backward lookback; prefix order `tools` → `system` → `messages`, with tool-definition changes invalidating everything. Claude Code manages caching itself (layers: system prompt + tools, project context, conversation), gets a 1-hour TTL on the main conversation for subscription users, and documents exactly which actions break the cache (model switch, effort change, MCP server connect without tool search, plugin MCP changes, bare-tool deny rules, compaction, image accumulation, upgrades) versus which keep it (file edits, CLAUDE.md edits, permission mode, skills, hooks, subagents). Verdict: **AUTO** in Claude Code; **CONFIG(`promptCacheTtl`, `subagentPromptCacheTtl`, `CLAUDE_CODE_PROMPT_CACHE_TTL`, `ENABLE_PROMPT_CACHING_1H`, `FORCE_PROMPT_CACHING_5M`, `DISABLE_PROMPT_CACHING*`)**; hooks are cache-safe by construction (hook output is appended as messages), and the statusline exposes `prompt_cache` and `context_window.current_usage` for monitoring.

### Cited Findings
**API mechanics**
- Default TTL 5 minutes with `"cache_control": {"type": "ephemeral"}`; "The lifetime is measured from the start of the request that writes or reads the entry. The cache is refreshed at no cost each time it is used."; 1-hour: `"cache_control": {"type": "ephemeral", "ttl": "1h"}` — [Prompt caching (API)](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Pricing multipliers: 5-minute write 1.25x base input; 1-hour write 2x; read 0.1x, except Fable 5.1 and Mythos 5.1 reads at 0.025x and Opus 5.5 / Sonnet 5.5 at 0.05x. Examples ($/MTok): Opus 5.5 $4 in / $5 5m-write / $8 1h-write / $0.20 read; Sonnet 5.5 $2 / $2.50 / $4 / $0.10; Fable 5.1 $10 / $12.50 / $20 / $0.25; Opus 4.6 $5 / $6.25 / $10 / $0.50; Sonnet 4.6 $3 / $3.75 / $6 / $0.30; Haiku 5.5 (≤100K) $0.10 / $0.125 / $0.20 / $0.01 — [Prompt caching (API)](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Minimum cacheable length: 512 tokens (Fable 5.1, Mythos 5.1, Opus 5.5, Opus 5, Sonnet 5.5, Fable 5, Mythos 5, Haiku 5.5); 1,024 (Opus 4.8, Sonnet 5, Sonnet 4.6, Sonnet 4.5, Opus 4.1, Opus 4, Sonnet 4); 2,048 (Mythos Preview, Opus 4.7, Haiku 3.5); 4,096 (Opus 4.6, Opus 4.5, Haiku 4.5). "If both `cache_creation_input_tokens` and `cache_read_input_tokens` are 0, the prompt was not cached." — [Prompt caching (API)](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Breakpoints: "Up to 4 explicit cache breakpoints per request"; automatic caching is a top-level `"cache_control": {"type": "ephemeral"}` field and uses one of the 4 slots; cache reads walk backward "up to 20 positions (the breakpoint counts as the first)"; "A run of consecutive `tool_use` blocks counts as one position, and so does a run of consecutive `tool_result` blocks." — [Prompt caching (API)](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Order/invalidation: "The cache prefix order is `tools` → `system` → `messages`. A change at one level invalidates that level and all later levels." Table: tool definitions invalidate tools+system+messages; web search toggle, citations toggle, speed setting invalidate tools only... ; tool choice and images invalidate tools+system; "Thinking parameters" and "Effort setting" are "Model-specific"; "Dropped thinking blocks" invalidate tools+system. "Setting effort explicitly to the model default is equivalent to omitting it and does not invalidate." Appending a `{"role": "system"}` message in `messages` adds an instruction without invalidating (not on Sonnet 5). Mid-conversation tool changes beta header: `inline-tools-2026-09-15` — [Prompt caching (API)](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Thinking in multi-turn: thinking blocks cannot take `cache_control`; "On Opus 4.5+, Sonnet 4.6+, and Haiku 5.5, thinking blocks are preserved by default, so the cache stays valid when non-tool-result user content is added. On earlier Opus and Sonnet models, and Haiku models through Haiku 4.5, adding non-tool-result user content strips previously cached thinking blocks and invalidates the cache from that point." — [Prompt caching (API)](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Stable-prefix guidance: "Place `cache_control` on the last block whose prefix is identical across the requests you want to share a cache"; put the breakpoint "at the end of the static prefix, not on the varying block" (timestamp example: "every request writes a new entry and none are read"); "In a growing conversation, the final block works as long as each turn adds fewer than 20 blocks."; "Cache hits require 100% identical prefix content"; cache isolated per organization (and per workspace on some platforms); "A cache entry becomes available only after the first response begins." — [Prompt caching (API)](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Usage fields: `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, `cache_creation.ephemeral_5m_input_tokens`, `cache_creation.ephemeral_1h_input_tokens`; `total_input_tokens = cache_read_input_tokens + cache_creation_input_tokens + input_tokens` — [Prompt caching (API)](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

**Claude Code's cache behaviour**
- "At Claude Code, we build our entire harness around prompt caching."; "we run alerts on our prompt cache hit rate and declare SEVs if they're too low."; "The best way to do this is static content first, dynamic content last."; "we add a <system-reminder> tag in the next user message or tool result with the updated information for the model, which helps preserve the cache."; plan mode: "we keep _all_ tools in the request at all times and use EnterPlanMode and ExitPlanMode as tools themselves... (Thariq Shihipar, Apr 30, 2026) — [Lessons from building Claude Code: Prompt caching is everything](https://claude.dev/blog/lessons-from-building-claude-code-prompt-caching-is-everything/)
- Layer table: "System prompt | Core instructions, tool definitions | The set of loaded tool definitions changes"; "Project context | CLAUDE.md, auto memory, unscoped rules | Session starts, or after `/clear` or `/compact`"; "Conversation | Your messages, Claude's responses, tool results | Every turn". "Plan mode and skill loading... append their instructions as conversation messages, so the cached prefix stays intact." - Actions that invalidate: Switching models ("Each model has its own cache"), Changing effort level (except on Opus 5.5/Sonnet 5.5/Haiku 5.5/Fable 5.1 with API key or subscription, v2.1.260+), Turning on fast mode, Connecting or removing an MCP server (only when tools load upfront; with tool search "Claude Code keeps the tool list from the conversation's first request for the whole conversation"), Enabling/disabling a plugin that provides MCP servers, Denying an entire tool (bare `Bash` deny rule, only without tool search), Compacting the conversation, Accumulating many images (oldest removed in batches), Upgrading Claude Code — [How Claude Code uses prompt caching](https://code.claude.com/docs/en/prompt-caching)

- TTL buckets: main conversation ("your interactive turns, non-interactive `-p` runs, and Agent SDK turns") gets one hour on a Claude subscription within plan usage, five minutes on usage credits/API key/cloud; "Everything else" (subagents, workflows, teammates, forks, compaction, session titles) five minutes. - Disable: `DISABLE_PROMPT_CACHING`, `DISABLE_PROMPT_CACHING_HAIKU`, `DISABLE_PROMPT_CACHING_SONNET`, `DISABLE_PROMPT_CACHING_OPUS`, `DISABLE_PROMPT_CACHING_FABLE` — [How Claude Code uses prompt caching](https://code.claude.com/docs/en/prompt-caching)
- Cache scope: "the cache is effectively scoped to one machine and directory. - Compaction and resume: "Claude Code reuses the system prompt layer [after compaction]... - Observability: `/usage` line `Prompt cache (main): 14 requests · 91% of input tokens from cache · 2 misses (...) · 1 expected rebuild (compaction or tool-result clearing) · warm (1h TTL, last activity 40s ago)` (v2.1.251+); "likely cause: tool definitions changed" (v2.1.260+); statusline `prompt_cache` object; `context_window.current_usage` with `cache_creation_input_tokens` / `cache_read_input_tokens` — [Manage costs](https://code.claude.com/docs/en/costs); [Customize your status line](https://code.claude.com/docs/en/statusline)

- Agent SDK: `systemPrompt` preset `excludeDynamicSections: true` moves per-session context into the first user message "for better prompt-cache reuse across machines"; `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` splits static/dynamic parts of a custom prompt; `snapshot: false` rebuilds the prompt every request — [Agent SDK TypeScript reference](https://code.claude.com/docs/en/agent-sdk/typescript)

### Inferences
- For a plugin, the cache-safe channels are exactly the ones hooks already use: `additionalContext`, `updatedToolOutput`, `updatedInput`, and `systemMessage` all land in the conversation layer. The things a plugin must avoid are anything that changes the tool list or system prompt mid-session (e.g., toggling an MCP server from a hook, or a `PreToolUse` deny rule with a bare tool name when tool search is unavailable).
- Content a plugin injects every turn (e.g., a timestamped budget line) is fine for the cache as long as it is appended, but it still costs uncached input tokens each turn and is summarized away at compaction ("Context that hooks added earlier | Summarized with the rest of the conversation").
- A plugin that wants post-compaction state to persist should use the SessionStart `compact` matcher rather than relying on earlier injected context.

- The API prompt-caching page was read only to ~100 KB of 160 KB; the remainder (pre-warming, server-side-tool details) was not reviewed.

## Key Question 5: Anthropic engineering guidance ("Effective context engineering" and related posts) — concrete recommendations with quotes

### Takeaway
Anthropic's guidance (Sep 2025 → Apr 2026) consistently says: find "the smallest set of high-signal tokens", prefer just-in-time retrieval over pre-loading, compact by summarizing while preserving decisions and open bugs, use tool-result clearing as the lightest-touch compaction, keep structured notes outside the window, isolate verbose work in sub-agents that return 1,000–2,000-token summaries, and design the harness around prompt caching (static prefix first, dynamic content last, updates via `<system-reminder>` messages).

### Cited Findings
- Definition: context engineering is "curating what will go into the limited context window"; goal is the "smallest possible set of high-signal tokens"; context rot: "the model's ability to accurately recall information from that context decreases" as tokens grow; "LLMs have an "attention budget" that they draw on when parsing large volumes of context." (Sep 29, 2025) — [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- System prompts: "The right altitude is the Goldilocks zone between two common failure modes." Tools "should be self-contained, robust to error, and extremely clear with respect to their intended use." Examples: "curate a set of diverse, canonical examples that effectively portray the expected behavior of the agent." — [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Just-in-time retrieval: agents "use these references to dynamically load data into context at runtime using tools."; Claude Code can "leverage Bash commands like head and tail to analyze large volumes of data."; "primitives like glob and grep allow it to navigate its environment and retrieve files just-in-time." — [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Compaction: "Compaction is the practice of taking a conversation nearing the context window limit"; keep "architectural decisions, unresolved bugs, and implementation details" while "discarding redundant tool outputs or messages."; Claude Code: "we implement this by passing the message history to the model to summarize and compress the most critical details."; "One of the safest lightest touch forms of compaction is tool result clearing" — [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Structured note-taking: the agent "regularly writes notes persisted to memory outside of the context window."; NOTES.md cited as an example for "your custom agent"; Pokémon example: "for the last 1,234 steps I've been training my Pokémon in Route 1, Pikachu has gained 8 levels toward the target of 10." — [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Sub-agents: each "return[s] only a condensed, distilled summary of its work (often 1,000-2,000 tokens)." Conclusion: "find the smallest set of high-signal tokens that maximize the likelihood of your desired outcome." — [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Agent SDK post (Sep 29, 2025): "The file system represents information that could be pulled into the model's context."; "the folder and file structure of an agent becomes a form of context engineering."; "Semantic search is usually faster than agentic search, but less accurate, more difficult to maintain, and less transparent."; "we suggest starting with agentic search, and only adding semantic search if you need faster results"; subagents "use their own isolated context windows, and only send relevant information back to the orchestrator"; loop: "gather context -> take action -> verify work -> repeat." — [Building agents with the Claude Agent SDK](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)
- Long-running harness post (Nov 26, 2025): "they must work in discrete sessions, and each new session begins with no memory of what came before"; "However, compaction isn't sufficient."; initializer agent writes "a claude-progress.txt file that keeps a log of what agents have done" and a feature list in JSON because models are less likely to overwrite JSON than Markdown; each session should "Read the git logs and progress files to get up to speed", "choose the highest-priority feature that's not yet done", and "End the session by writing a git commit and progress update."; "work on only one feature at a time" was "critical to addressing the agent's tendency to do too much at once." — [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Prompt-caching post (Apr 30, 2026): "A high prompt cache hit rate decreases costs and helps us create more generous rate limits for our subscription plans"; fork pattern for "side computation (compaction, summarization, skill execution)" reuses the parent's cache "at one tenth the price"; compaction summary "about 20k tokens" — [Lessons from building Claude Code: Prompt caching is everything](https://claude.dev/blog/lessons-from-building-claude-code-prompt-caching-is-everything/)
- Claude Code docs operationalize this: "Instead of Claude reading a 10,000-line log file to find errors, a hook can grep for `ERROR` and return only matching lines, reducing context from tens of thousands of tokens to hundreds."; worked example PreToolUse hook rewrites `npm test|pytest|go test` to `... 2>&1 | grep -A 5 -E '(FAIL|ERROR|error:)' | head -100` via `hookSpecificOutput.updatedInput`; "Delegate these to subagents so the verbose output stays in the subagent's context while only a summary returns"; "Aim to keep CLAUDE.md under 200 lines" — [Manage costs](https://code.claude.com/docs/en/costs)
- Third-party (secondary, unverified): a Claude Code engineer's April 15, 2026 session guide reportedly maps session states to `/compact <hint>` vs `/clear` — [hyperdev.matsuoka.com](https://hyperdev.matsuoka.com/p/how-claude-code-got-better-by-protecting)

### Inferences
- The Claude Code costs page is Anthropic's own worked example of "replicating context engineering via hooks": PreToolUse `updatedInput` to filter command output, skills for on-demand knowledge, subagents for isolation. These map directly onto what a hooks-only plugin can do.

## Key Question 6: Claude Agent SDK / Claude Code context-management options and what hooks can reach

### Takeaway
The Agent SDK exposes `maxTurns`, `maxBudgetUsd`, `thinking` (default `{ type: 'adaptive' }`), `effort`, `taskBudget` (alpha), `systemPrompt` cache controls, per-agent `autoCompactWindow`, and `Query.getContextUsage()` (returns `autoCompactThreshold`, `isAutoCompactEnabled`, `maxTokens`), but no `compaction_control`-style option; compaction is the same client-side Claude Code pass. Hooks give a plugin: context injection (SessionStart incl. `compact` matcher, UserPromptSubmit, PreToolUse, PostToolUse, Stop `additionalContext`), tool-input rewriting (`updatedInput`), tool-output replacement (`updatedToolOutput`), compaction veto (PreCompact exit 2 / `decision: block`), and read-only access to `compact_summary` (PostCompact). The statusline receives `context_window.*` and `prompt_cache` every refresh.

## Key Question 7: Extended thinking and context — are earlier-turn thinking blocks dropped, and does it depend on model or beta flag?

### Takeaway
It depends on the model, not a beta flag: "Keep all prior turns" on Opus 4.5+, Sonnet 4.6+, Haiku 5.5, Fable 5/5.1, Mythos 5/5.1/Preview (retained blocks "count as input like any other conversation history"); "Keep the last turn only" on earlier Opus/Sonnet and Haiku ≤ 4.5 ("the API strips them automatically"). "No code changes or beta headers are required"; the override is the `clear_thinking_20251015` context-editing strategy. Manual `thinking.type: "enabled"` with `budget_tokens` is deprecated on 4.6 and rejected on 4.7+ in favour of `{type: "adaptive"}` + `output_config.effort`. Fable 5.1 / Opus 5.5 / Sonnet 5.5 / Haiku 5.5 add a prefix check: client-side edits to earlier turns invalidate later thinking blocks, enforced as errors for accounts created on/after 2026-08-31 unless `thinking.block_binding.prefix_mismatch_behavior: "drop_block"` is sent with `thinking-binding-controls-2026-08-01`. Verdict: **AUTO** (server-side); **CONFIG(`MAX_THINKING_TOKENS`, `alwaysThinkingEnabled`, `CLAUDE_CODE_EFFORT_LEVEL`, `effortLevel`, `modelSettings`, `CLAUDE_CODE_DISABLE_ADAPTIVE_THINKING`)** in Claude Code; the clearing strategy is **API-ONLY**.

### Inferences
- On every current default Claude Code model (Opus 5.5, Sonnet 5.5, Haiku 5.5, Fable 5.1, and the 4.6+ line) prior-turn thinking is retained and billed as input, so thinking is a real contributor to context growth that only compaction (or the API-only `clear_thinking_20251015`) removes; a plugin's token estimates should treat thinking as persistent on these models.
- Because the preserved-thinking prefix check treats a cleared/shortened `tool_result` as an invalidating edit, Claude Code's client-side tool-result clearing must be implemented as a prefix-preserving rewrite (which the docs classify as an "expected rebuild"); a plugin should never attempt to rewrite earlier transcript turns itself.

### Gaps
- The thinking page does not state the default `keep` value that `clear_thinking_20251015` applies per model beyond "model-specific" (the context-editing page gives the tiers).
- Whether Claude Code sends `thinking.block_binding.prefix_mismatch_behavior` or the `thinking-binding-controls-2026-08-01` beta is undocumented.

### Inferences
- The plugin's highest-leverage, Anthropic-endorsed moves are (a) PreToolUse `updatedInput` / PostToolUse `updatedToolOutput` to keep verbose tool output out of context, (b) SessionStart `compact` re-injection of a compact handoff brief, (c) using `context_window.used_percentage` from the statusline to time nudges (noting it measures against the full model window, not a lowered `autoCompactWindow`), and (d) recommending (not setting) `autoCompactWindow`, `ENABLE_TOOL_SEARCH`, `MAX_MCP_OUTPUT_TOKENS`, and the 1-hour TTL settings.
